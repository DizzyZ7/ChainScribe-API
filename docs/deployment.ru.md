# Регламент production-развертывания

[English version](deployment.md)

## Предварительные условия

- CI успешно завершен для точного коммита, который выпускается.
- Образ собран из этого коммита и помещен в приватный реестр или реестр с контролем доступа.
- PostgreSQL и Redis доступны только из сети приложения.
- Для PostgreSQL включены TLS, шифрование данных на диске, автоматические резервные копии и восстановление на выбранный момент времени.
- Настроены DNS, TLS-сертификат, обратный прокси и WAF.
- Релиз принят внешней проверкой безопасности.

## Секреты

Создайте независимые случайные значения для Django и подписи JWT. Храните их в управляемом хранилище секретов, а не в `.env`, добавленном в Git.

Ограничьте учетные данные базы данных только базой приложения. Ротация всех секретов должна выполняться по заранее проверенной процедуре.

## Последовательность релиза

1. Создайте резервную копию PostgreSQL и проверьте ее метаданные.
2. Получите или соберите неизменяемый образ приложения.
3. Выполните `python manage.py migrate --noinput` как отдельную release-задачу в одном экземпляре.
4. Запустите один canary-экземпляр с отключенными автоматическими миграциями.
5. Проверьте `/api/v1/health/live` и `/api/v1/health/ready` через обратный прокси.
6. Сначала выполните `scripts/smoke_test.py` со специальной тестовой учетной записью или в staging-среде.
7. Разверните остальные экземпляры и контролируйте задержки, а также частоту ответов 401, 403, 429 и 500.
8. Сохраните предыдущий образ для отката.

Откат базы данных зависит от конкретной миграции. Нельзя автоматически выполнять обратные миграции после того, как приложение уже записывало данные по новой схеме. Предпочтительнее выпускать исправляющую миграцию вперед, если обратная операция не была заранее проверена.

## Требования к обратному прокси

- принудительно использовать HTTPS и современные версии TLS;
- сохранять проверенный `X-Request-ID` либо позволять приложению создать его;
- устанавливать `X-Forwarded-Proto: https`;
- перезаписывать, а не дополнять недоверенные forwarding-заголовки;
- ограничивать размер заголовков и тела запроса до передачи в Gunicorn;
- применять более строгие лимиты к endpoint аутентификации;
- не записывать authorization-заголовки и query string в access-логи;
- публиковать только порт приложения, не открывая PostgreSQL и Redis.

Устанавливайте `TRUST_PROXY_HEADERS=true` только тогда, когда запросы могут поступать исключительно через доверенный обратный прокси.

## Плановые задачи

Ежедневно выполняйте:

```bash
python manage.py flushexpiredtokens
```

Проверку резервных копий и учебные восстановления необходимо планировать отдельно от приложения.

## Мониторинг

Настройте оповещения о продолжительных ошибках readiness, перегрузке базы данных, недоступности Redis, всплесках 500, необычно высокой доле отказов аутентификации и резком росте срабатываний rate limiting.

Связывайте события по `X-Request-ID`. Не собирайте тела запросов и учетные данные даже во время расследования инцидентов.
